# fespalier — agent guide

File-tree routing for Flutter. Plain widgets and functions in `lib/app/` (`page.dart`, `data.dart`,
`layout.dart`, `guard.dart`, ...) become one typed `go_router` entry point, `lib/app.g.dart`,
written by a Rust generator (`fsp`). A Dart package carries the runtime that generated file
imports. `README.md` (the short entry point) and `docs/` (one page per topic) are the user documentation;
read the section for the file kind you touch before changing how it behaves.

Its rules: `validate()` first (a refusal throws at once, like an action's); the last run wins (a `call` cancels the run in progress, which ends cancelled; the `Future` of any run that ends cancelled (`cancel()`, `reset()`, a newer run, a dispose) fails with the public `StreamActionCancelled` (`latest`, `count`, no value in its `toString`) and is `.ignore()`d, so a run nobody awaits reports nothing, while the hook's `call` stays quiet and returns null); a run lives while the provider is watched, and the provider's `onDispose` cancels the subscription (no `ref` after that: nothing written or invalidated), while `call(hold: true)`, what the generated `submit` (`runActionStream`) does, holds a `keepAlive` link to the stream's end, like a `Future` action; only the stream's own body and `listen` are inside `telemetryWithin` (the handlers run through the caller's `Zone`, so a state write, a `ref.listen` it wakes and `_invalidate` are not children of the ended span); `call` checks `_alive` and `ref.mounted` first (a `StateError`, nothing started) and moves the keep-alive and the first state write inside its `try`, so any throw ends the run once through `_failed`; what the action makes stale is invalidated on done and on a cancel or a failure after at least one item (a partial write is a write), never for a failure before the first item and never from `onDispose`; `FieldErrors` end it as `StreamFailed`. Telemetry is one action span per run, `TelemetryEnd.actionItems` and the outcome `cancelled` (contract version 1, additive; `fespalier.action.items` in `fespalier_otel`, `ok` status in `fespalier_sentry`, which never sends the count); DevTools sees the existing start and end, never once per item, and no `items` key yet. Its one listener is the subscription on the action's stream: `test/no_timers_stream_action_test.dart` greps the file. `examples/features`' `docs/new/action.dart` is its example. Not published to a registry: apps use it as a git dependency at a release tag. ## Running one suite

- One Rust unit test: `cd cli && cargo test <name>` (a module: `cargo test resolve::`). One
  integration file: `cargo test --test cli`. Tests that compare with `dart format` skip when
  `dart` is not on `PATH`, so put Flutter's `bin/` there before trusting a green run.
- The package: `cd packages/fespalier && flutter pub get && flutter test`; one file:
  `flutter test test/guards_test.dart`.
- One example: `cd examples/<name> && flutter pub get && flutter test`.
- A workspace package: `flutter pub get` there resolves the whole workspace at the root;
  `dart run melos run check --scope=fespalier_http` runs CI's three steps for one package.
- The generator on an example: `cd cli && cargo run -- check --project ../examples/shop`.
- Release scripts: `python3 scripts/test_packaging.py` (and the other `scripts/test_*.py`).
- The editors: `cd editors/vscode && npm ci && npm test`; `cd editors/intellij && ./gradlew build`.

A filtered run is feedback, not verification; `just ci` still has to pass.

## Conventions

- **Conventional Commit PR titles.** The repository squash-merges, so the PR title becomes the one
  commit on `main`, and release-please reads only that. `feat:` and `fix:` decide the version;
  `docs:`, `ci:`, `build:`, `style:`, `refactor:`, `perf:`, `test:`, `chore:` and `revert:` are
  patches. `pr-title.yml` refuses anything else and also parses the whole squash message with
  release-please's own grammar, so a body line starting with a call-like token with nested
  parentheses (`A(B(c)) ...`) fails it. Commits on a branch need not be conventional; the title
  and the body must parse. Do not bump versions or edit `CHANGELOG.md` or
  `.release-please-manifest.json` by hand: release-please does (see `docs/releasing.md`).
- **Squash merges**, so cite "PR #N" rather than a branch commit.
- **What only a device can show gets a beginner-friendly issue.** A behaviour no test can see (a platform
  view drawing, a system prompt, a notification tap, a hardware key) is not claimed as verified: file a
  `good first issue` with step-by-step setup, the cases to try, what "works" looks like and what to report
  (device, OS, versions), as #130–#133 do.
- **Native code is welcome when it makes things faster or sturdier, as long as the app developer notices nothing.**
  Kotlin, Swift, or Rust or C through FFI, as `otel_zone`'s crash capture and the MapLibre plugin do. The seam must be
  clean: the same Dart API, no extra setup step, a no-op or pure-Dart fallback where the native side is missing, and
  fakes so a widget test never reaches a platform channel. It follows fespalier's rules too: no per-frame or
  per-navigation work on the UI thread that a cheaper path avoids, nothing sensitive persisted or sent, and every
  behaviour no CI test can show is written as UNCHECKED in the docs and gets the beginner-friendly issue the bullet
  above describes (labelled `human-test` and `good first issue`).
- **Actions are pinned to a full commit SHA** with a `# vX.Y.Z` comment, resolved with
  `git ls-remote https://github.com/<owner>/<repo> refs/tags/<tag>` (add `^{}` for an annotated
  tag), preferring the versions the org repositories already pin. Workflows declare
  `permissions: {}` or `contents: read` and grant more per job, set `timeout-minutes` and a
  `concurrency` group, use `persist-credentials: false` on checkouts that do not push, and never
  put `${{ }}` inside `run:` (pass values through `env:`). The org lint runs zizmor and
  actionlint, so run them on workflow changes. `on.pull_request.paths` is never used: gate jobs
  with an `if:` over the paths-filter job in `quality.yml`.
- **Docker images are pinned by tag and multi-arch index digest** (`image:tag@sha256:...`, in
  `cli/templates/telemetry/compose.yaml`; a test checks the form). To bump one, edit the tag, resolve
  the digest with `docker buildx imagetools inspect <image>:<tag>` (its `Digest:` line, with an
  `amd64` and an `arm64` entry below it), and run `just telemetry-smoke`.
- **Regenerate the examples.** After changing the emitter, a template or `manifest.rs`, run
  `just gen-examples` and commit the new `lib/app.g.dart` files; a generator test fails on a stale
  one. Generated files stay unformatted (the `format:` option is off) so they do not depend on the
  Dart SDK; `dart format` checks skip `*.g.dart`, except that `examples/minimal` sets
  `format: true`.
- **Scaffolds are formatted.** What `fsp init` and `fsp new` write must be what `dart format`
  leaves alone; `cli/templates/new/_macros.dart.jinja` lays out long names the way the formatter
  does. Change a template, and `scaffolded_files_are_dart_format_clean` tells you.
- **Rust.** Edition 2024, `rustfmt.toml` (max width 100), `[lints]` in `cli/Cargo.toml`
  (`unsafe_code` forbidden, clippy pedantic as a warning, `unwrap_used` / `expect_used` warn).
  Allow a lint only with a reason, at module level or in `[lints]`. Tests may unwrap.
- **Dart.** `flutter_lints` everywhere; the package also runs strict casts, inference and raw
  types, and requires a doc comment on every public member (`public_member_api_docs` is an
  error). File names are `snake_case`. The package is published nowhere (`publish_to: 'none'`).

## Things that bite

- `cargo` only honours `cli/rust-toolchain.toml` from inside `cli/`; run it there, not with
  `--manifest-path` from the root.
- `dart format` picks its style from the package's language version, so format after
  `flutter pub get`; the examples declare an older SDK than the package.
- Adding a file kind or a binding rule touches the resolver, the emitter, the docs section,
  the examples and usually `manifest.rs` (the `fsp routes --json` fields); the editors read that
  JSON, so keep it additive.
- **The skills move with the code.** A new heading in README.md or docs/\*.md, file kind, `fespalier:` config key or
  `fsp` command fails `just skills` until a skill covers it (prose in the owning skill, its
  diagnostics in `fespalier-troubleshooting`, the id in `skills/coverage.json`). A changed
  message, behaviour or docs claim needs the skill pages that quote it updated too: grep
  `skills/` for the old text. Say the release a change lands in ("since 0.5.0"), since apps
  pin older ones; `skills/README.md` has the rules.
- **Types are compared by what they name, spelling first (since 0.21.0).** `types.rs` makes a type canonical only when two spellings differ, and a by-type lookup tries the exact spelling first, so an app that spells each type the same wherever it is compared generates the same code (the three cases where a typedef or a prefix changes it are in the 0.21.0 migration notes); it reads only the app's files and, since 0.22.0, its `path:` dependencies' (`packages.rs` finds them in the pubspecs as pub does: `pubspec_overrides.yaml` and a pub workspace root's overrides included, a `..` resolved in the text and never through a symlink) through `Libs`, never `.dart_tool/`, `pubspec.lock` or the pub cache, so `fsp check` is the same before and after `pub get`; `fsp watch` watches, non-recursively, the folders of what a pass read outside `lib/` (`Reads::folders`) and asks for them again on every pass, since inotify drops the watch of a folder that is deleted and made again. No analyzer: `types_tests::follows_typedefs_as_the_analyzer_does` checks it against `dart analyze` instead.
- **build_runner can delete `lib/app.g.dart`.** The builders that write `.g.dart` files (json_serializable,
  riverpod_generator) claim an `X.g.dart` for every `X.dart`, so an app with a `lib/app.dart` loses fespalier's
  default output on the next `dart run build_runner build`, with nothing logged (it deletes conflicting outputs on its
  own since 2.7.0, so `-d` is ignored and the docs leave it out). `cli/src/build_runner.rs` warns from `gen`, `check`
  and `watch`; any doc that shows `build_runner` in `tasks:` says `output:` is the way out. A freezed `extra` is a
  private `_Note`: `ExtraCodec({Note: ...})` looks types up exactly and saves it as `null`; `ExtraCodec.of` matches
  with `is`. Both are reproduced by `just codegen-interop`.
- **The schema moves with `config.rs` (since 0.23.0).** A key or a task key added to `config.rs` or `tasks.rs` fails `schema_tests` until `cli/schema/fespalier.schema.json` has it (with a `description` that says "since 0.23.0", and a `default` when there is one). Then `FSP_UPDATE_GOLDEN=1 cargo test schema_tests::` in `cli/` writes the two editor copies, and they are committed with it. Never edit the copies by hand.
- **The DevTools extension's build is committed.** After touching `packages/fespalier_devtools/`,
  `packages/fespalier/lib/src/devtools/protocol.dart` or `FLUTTER_VERSION` in `ci.yml`, run
  `just devtools-build` and commit `packages/fespalier/extension/devtools/build/` with the change; CI
  rebuilds it and compares byte for byte, so a Flutter bump fails the `devtools` job until someone
  does. Do not run `dart run devtools_extensions build_and_copy`: it adds 37 MB of CanvasKit, a service
  worker with a random version and every Material icon. The protocol file has one source,
  `packages/fespalier/lib/src/devtools/protocol.dart` (it imports nothing); the extension holds a copy
  that the build script refreshes and a test compares. The extension's `pubspec.lock` is committed on
  purpose (a build must not change when a dependency publishes) and has no `fespalier` in it, which is why
  the protocol is copied and not a path dependency: a release bump would make the lock stale.
  `config.yaml`'s `version:` is release-please's, like the pubspec's. Protocol additions stay protocol 1 only
  while they are optional: a new method, event, record or feature name, and a key whose absence reads as its
  default (the adapters of 0.16.0, `DevToolsAdapters` and the Adapters tab, are the model; an older app sends
  no `adapters`).
- **fespalier must not make apps flaky.** Everything the DevTools support adds sits behind
  `kFespalierDevTools` (a `const`, false in release), so a release build has none of it (CI greps a
  release build for `ext.fespalier`); in debug it starts no timer, schedules no frame, reads no
  provider and wraps every path in a `try`. `app.g.dart` calls `devToolsRegister` and `devToolsAttach`:
  never remove them by hand, and keep new calls under `if (kFespalierDevTools)`. The calls that follow
  the guards, the data and the actions (`traceGuard`, `traceData`, an action's `site:`) are not under an
  `if`: they are **pass-through wrappers** that return their last argument, the very object, so a sync
  guard or `data()` stays sync (no `Future`, no microtask) and a `Future` is never replaced; `devtools_trace_test.dart`
  checks it, and in release they are the identity and dart2js inlines them away (the scaffold CI job
  greps a release build with a guard, a `data.dart` and an action in it). Keep them that way: no provider
  read, no listener on a provider or a stream, no timer. The outermost call of a generated `redirect:`,
  `runRedirect` (since 0.21.0), is not one of them: it returns a sync answer as it is and turns a failure into
  a `GuardFailure`, and for an async guard gives go_router a `Future` of its own, run outside go_router's error
  zone on 17.2.3 to 18.1.0; it makes no `Future`, microtask or timer for a sync guard, and `traceGuard` inside
  still sees the guard's own result.
- **A pushed page's guard is known by go_router's own objects (since 0.21.0).** `packages/fespalier/lib/src/guards.dart`
  keeps a pushed entry's guards by the entry's `ImperativeRouteMatch.completer`, and tells a navigation by the
  `RouteInformationState` it put in the provider. It listens to the delegate and to nothing else: no provider listener,
  no zone that tells one navigation from another, no timer, no new microtask, only post-frame callbacks
  (`test/no_timers_guards_test.dart` reads the source for it). The one flag, `_landing`, lives exactly as long as the
  synchronous `router.replace` call of a re-run. An asynchronous re-run never lands: it is dropped at its first
  asynchronous answer and carried on, while its entry is on top and it is the entry's newest re-run, by a re-run that
  replays the answers by position, each to the redirect (route and location) that gave it (a chain that meets another
  redirect twice is not carried again). Six
  reviews failed by giving an identity to something else (the provider's value, a count of its notifications, a zone, a
  copy of the last request, a table of re-runs), each time leaking one navigation's identity into another: read the
  invariants in the class comment before changing it, and do not add a mechanism that says which navigation is on the way.
- **Telemetry costs nothing when off, and never makes async.** An app generated without `telemetry: true`
  passes no `TelemetrySite`, so every `telemetry:` parameter (`traceGuard`, `traceData`, `ActionNotifier`,
  `DeferredLibrary(route:)`) is null and the code behind it is compiled out; the scaffold CI job greps a
  release web build for `fespalier telemetry` (the line `telemetry.dart` prints when a sink throws), and
  also builds an app with an `observe.dart`, which must not pull telemetry in. `telemetry.dart` and the
  watch in `lifecycle.dart` never create a `Future`, a microtask or a timer: a sync guard, `data()` or
  action is reported in the same call stack, an async one through a side `then` with its own `onError`,
  and the wrappers return the very object. A hook runs after the frame, never in `build`, with the `Ref`
  of a throwaway provider that has finished building (Riverpod forbids changing a provider during
  another's build). The names `fespalier_otel` emits are contract version 1 (`docs/observability.md`, "Telemetry
  conventions"): adding is fine, renaming or removing is a breaking release.
- **The companion packages are pinned together.** `fespalier_otel`, `fespalier_transport`, `fespalier_auth`, `fespalier_oidc`, `fespalier_keypair`, `fespalier_keypair_dpop`, `fespalier_image`, `fespalier_http`, `fespalier_dio`, `fespalier_cratestack`, `fespalier_sentry`, `fespalier_tolgee`, `fespalier_forms`, `fespalier_maps`, `fespalier_download`, `fespalier_download_background` (which also depends on `fespalier_download`), `fespalier_push`, `fespalier_analytics`, `fespalier_launch` (since 0.18.0) and `fespalier_stream` (since 0.25.0) depend on `fespalier`, `fespalier_oidc` and `fespalier_sign_keypair` on `fespalier_auth` (and `fespalier_keypair_dpop` on `fespalier_oidc`, `fespalier_sign_keypair` on `fespalier_keypair`, and, since 0.25.0, `fespalier_frb` and `fespalier_cratestack` on `fespalier_stream`), by git at the release tag, and `cli/tests/versions.rs` reads every `ref: v…` in their pubspecs and READMEs (and in `docs/*.md`) as fespalier's own version, so an app must write the same `url` and `ref` for all of them. A dependency of another repository that is pinned by tag must be pinned by commit instead, or that test reads it as fespalier's.
- **Everything that sends HTTP sends through `fespalier_transport` (since 0.21.0).** `fespalier_auth`, `fespalier_oidc`,
  `fespalier_keypair`, `fespalier_keypair_dpop`, `fespalier_sign_keypair`, `fespalier_download`, `fespalier_tolgee`,
  `fespalier_image`, `fespalier_cratestack`, `fespalier_otel`, `fespalier_sentry`, `fespalier_stream` (since 0.25.0) and
  `fespalier_transport` itself must not
  depend on `package:http` or `package:dio` (`fespalier_maps` and `fespalier_download` may have `http` as a dev dependency
  for tests): only `fespalier_http` and `fespalier_dio` implement the interface. Each has a `test/no_http_test.dart` that
  greps `lib/` and the pubspec, so a new `import 'package:http/...'` fails there, not in review. A new package that
  sends a request takes an `HttpTransport` (a constructor argument or a provider the app overrides) and gets the same
  test. Two rules every decorator keeps, because the session above it relies on them: it **passes
  `TransportRequest.attributes` through unchanged** (`request.copyWith(headers: ...)` keeps them; a fresh
  `TransportRequest(...)` drops them), and so the **`TransportMemo`** (`attributes['fespalier.memo']`, what a retrier's
  sends share) reaches the session, whose protection (a refused request is refused again, a request is never sent again as
  another user, one renewal per request) is kept in it; a decorator that drops it makes every send a first one with no
  error. A decorator also never reads a body it hands on (`TransportResponse.buffered` for that), starts no timer, and
  records no query, header value or body. `fespalier_keypair`, `fespalier_keypair_dpop` and `fespalier_sign_keypair`
  need Flutter 3.44 (flutter-sign-keypair), so they are outside the workspace and the `floor` job, in the `dart` matrix and
  the justfile's `outside_dirs`; the WebCrypto key is UNCHECKED in CI.
- **The pub workspace (since 0.21.0).** The packages that claim Flutter 3.35 are one workspace (the root
  `pubspec.yaml`): one resolution, and their git dependencies on each other resolve to the checkout. So a
  member has `resolution: workspace` and no `dependency_overrides`: pub refuses an override of a workspace
  package ("Cannot override workspace packages"), and a third-party override in one member would apply to all
  of them, so `cli/tests/versions.rs` refuses any. A new 3.35 package goes into `workspace:` and the `dart` and
  `floor` matrices (`cli/tests/versions.rs`; the justfile and `scripts/deps.sh` read the list, so an entry
  carries no comment). `flutter pub downgrade` inside a member downgrades
  every member together, so the floor runs copies (`scripts/floor_copy.py`, which overrides only the members
  a package reaches: pub adds every override to the resolution, used or not). Each third-party dependency is
  spelled one way in every pubspec, in the workspace or not (`every_third_party_dependency_has_one_constraint`,
  `SPELLING_EXCEPTIONS` for a reason), and in `fsp create`'s recipes
  (`the_recipes_spell_a_dependency_as_the_pubspecs_do`). The root `pubspec.lock` is not committed. Melos is
  the root's dev dependency, so it is part of the resolution the members are tested in; run it as
  `dart run melos ...`. Its pin is exact (`cli/tests/versions.rs`), so a new Melos is a deliberate edit; that
  does not freeze Melos's own dependencies (no root lockfile is committed). `pub upgrade --major-versions`
  rewrites an exact pin to `^<newest>`, so `scripts/deps.sh upgrade` writes it exact again.
- **`fespalier_adaptive/lib/material.dart` must compile on Flutter 3.35**, fespalier's floor. CI's `floor` job (`just floor` locally) checks it, but check a Material API's first release before using it: `NavigationDrawer.header` and `footer` exist from 3.35, so they could be slots, but today the scaffold puts `leading` and `trailing` into `children`. What it uses today (`NavigationBar`, `NavigationRail` and `NavigationDrawer`, and the `enabled` and `disabled` flags of their destinations) is compiled by the `floor` job on 3.35.7.
- **`fsp dev` is a pure state plus threads.** Every decision (hot reload or restart, coalescing, the
  shutdown, the device choice, the keys) is in `dev_state.rs` (a regeneration's reload or restart is `DevState::reloads`), which reads no clock, file or terminal and is
  driven with a `now` in tests; `dev.rs` is the I/O around it, and `dev_tui.rs` draws it (goldens in
  `cli/tests/golden/dev-tui/`, and `docs/images/fsp-dev.svg` from the same buffer: `FSP_UPDATE_GOLDEN=1 cargo
test dev_tui_tests::`). While the full-screen view is up **nothing may print to stdout or stderr**: route a
  message into a pane (an `Input::Line` or `Input::Notice`), not `eprintln!`. Every child runs in its own
  process group (`procs.rs`), and the tests that need flutter use a fake `flutter` script that speaks the
  daemon protocol, polling a log instead of sleeping.
- **Several telemetry sinks, and `within` (since 0.9.0).** `FespalierTelemetry.combine` gives each sink its
  own tokens and parents (`TelemetryStart._withParent` copies a start with a new parent: **a field you add to
  `TelemetryStart` goes there too**, and `telemetry_combine_test.dart` sets every field), and isolates each
  sink's errors. `within` is **synchronous and transparent**: `telemetryWithin` runs the body once, in the
  caller's error zone (a sink's own error handler is refused and printed once), and returns the very object,
  so a sync `data()` stays sync. Only an app made with `telemetry: true` calls `traceDataCall(..., () =>
data(...))`; the others keep `traceData`. A `fespalier_otel` convention is contract version 1: add a
  key, never rename one. Since 0.19.0 a sink also hears `commit(navigation, TelemetryCommit)` from `RouterWatch._committedForTelemetry` (and from a late `enableTelemetry`), synchronously in the delegate's notification and before the page is built (the first one while the `Router` builds). While the same sink stays installed, a committed navigation's `TelemetryEnd.route` is its last commit's `route`, because both come from `_routeOf` (a sink uninstalled between two commits of one navigation is not told the second); `FespalierOtel(onScreen:)` is told there, never at `end`.
- **Adapters and page names (since 0.9.0).** `fespalier: adapters:` imports
  `package:<name>/fespalier_adapter.dart` (a top-level `adapter`, a `FespalierAdapter`) for each entry and
  calls its members from the generated `main()`; the output depends on the pubspec alone, never on
  the pub cache or `pub get`, so `fsp check` is the same before and after. Since 0.11.0 the calls go through
  `AppAdapters`, which `app.g.dart` defines (a `FespalierAdapters` from `packages/fespalier/lib/src/adapters.dart`
  holds the order), whatever `main:` says, so `main: manual` apps call it from their own `main()`, and
  `AppRoutes.attach(router, container)` runs each adapter's `attach` once per router. `AppRoutes.router(launch:)` builds the router inside `launchRouter` (`links: true` with telemetry, `links: AppAdapters.handlesEnter` with adapters alone; the generated main passes it `AppAdapters.launch()`'s answer), and `AppRoutes.onEnter` exists **only with adapters** and is **passed to go_router only when an adapter has an `onEnter`** (`FespalierAdapter.onEnter` is a nullable getter that answers a `FespalierEnter` since 0.16.0, null by default, so a 0.15 adapter with an `onEnter` method fails to compile instead of being skipped: `onEnter: AppAdapters.handlesEnter ? onEnter : null`, and `FespalierAdapters.onEnter` asks only the adapters whose getter is not null): any `onEnter` makes go_router parse every navigation asynchronously and apply its redirect limit (a `go()` then a `push()` in one handler loses the `go()`), so an app whose adapters leave it alone keeps go_router's simplest code path (**every app's `app.g.dart` changed** in 0.11.0 for the `launchRouter` wrapper). Never pass `onEnter` unconditionally. Each page builder the generator
  writes is wrapped in `namedPage('<pattern>', () => ...)`, so **every app's `app.g.dart` changed** in
  0.9.0 (two lines per page builder): never hand-edit them, and a new place that builds a `Page` reads
  `Transitions.pageName`.
- **A paused stream stops reading; the app's tick closes it (since 0.25.0).** `fespalier_stream` never waits on its own: no
  timer, no backoff, no Riverpod retry. Riverpod pauses a stream while its watchers rebuild (keys + 1 times per event that
  concerns every key of a feed: `packages/fespalier_stream/test/pause_churn_test.dart` counts them), so a
  pause only stops reading and a connection is closed by `closeIfPaused` on the app's `streamTicker` only when it was
  already paused at the tick before. The tick reaches the connections through the `StreamTicker`'s list, never through a
  watch: a provider whose watchers are all paused is told nothing. A drop is a `LiveWaiting` status, never a stream error
  (an error would start Riverpod's retry timer). Keep all three when changing the package.
- **A provider that can fail says `retry:`.** Riverpod 3 retries a provider that fails with an `Exception` (a plugin's
  `PlatformException`, a store's error) after 200 ms, doubling, up to ten times, with a `Timer`: a hidden timer, and a
  pending one in any widget test whose fake throws. Every `FutureProvider`, `StreamProvider` and async notifier
  provider declared in a package's `lib/` passes `retry: (_, _) => null` (or its own policy); a sync provider fails only
  for a programming error (an `Error`), which is never retried. Each such package's `test/no_timers_test.dart` reads
  `lib/` and fails on a declaration without `retry:`.
- Every place that spells out the release version is annotated for release-please and checked by
  `cli/tests/versions.rs`, which reads the READMEs and every `docs/*.md`; if that test fails after your change, you moved or removed an annotation. A docs page that gains or loses an annotated block is added to or removed from `extra-files` in `release-please-config.json`.
  The annotation is for fespalier's own version only: release-please's updater replaces the first
  `x.y.z` on every line from a `start-version` marker to its end marker and on every line carrying
  the inline one, whoever's it is. A dependency's range (`sentry_flutter: ">=9.26.0 <10.0.0"`) inside
  a block was rewritten to the release's number in 0.9.0 and 0.9.1, so write such a range in prose or
  after the block's end marker, never in the snippet the block wraps.
- **No CDN secret in an app.** `fespalier_image` has no parameter for a key or a salt and ships no HMAC code; its
  `signer:` is a callback. Keep it that way: `crypto` is a dev dependency for the signing tests only, and
  `signing_test.dart` greps `lib/` for signature code. A key in a build (a constant, a `--dart-define`) is public.
- **No Tolgee API key in a release build.** `fespalier_tolgee`'s in-context code and the key (`String.fromEnvironment('TOLGEE_API_KEY')`, in `lib/src/in_context/editor.dart` alone, on a `kTolgeeInContext ?` line) stay behind `kTolgeeInContext`, which is a `const false` in release and profile builds; `TolgeeCdn` takes no key, and `TolgeeEditor`'s only constructor that takes one is `@visibleForTesting`. `no_secrets_test.dart` pins it. Docs say never to pass the key to `flutter build`. The panel is built under `kTolgeeInContext || (kDebugMode && TranslationScope.debugInContext)`, so it folds away in release. No timers, microtasks or listeners of its own either (`no_timers_test.dart`): the scope is built inside the Router's build, with the Router's listener forwarded.
- **`fespalier_cratestack` is offline-first, and the package stays pure.** It imports no CrateStack package, and the
  transport and the error reader are the seam: do not add a dependency on a generated client or on `cratestack_cbor`.
  If a CrateStack git dependency is ever needed, pin it by commit (`ref: <sha>   # cratestack 0.15.3`), never `ref: v0.15.3`,
  and keep its version number outside the release-please blocks. `lib/` starts no timer and listens to nothing
  (`no_timers_test.dart`): a trigger is a signal the app fires, and a sync is started by a side `then`, never from
  `build`. **A queued intent is never evicted, never expires and is wiped at sign-out** (`crateStackAccount.clear`):
  keep the durable store out of the budgeted storages. An intent is stored once, encoded, and every attempt sends those
  bytes under the same key unless the server gave a stored failure (the next key): changing the answer table or the key
  format changes the idempotency contract with the server, so it is a breaking release. Only a `CrateStackOffline` makes a
  read fall back to the device; a refusal is the answer. Nothing a server said (message, details) is stored in an intent
  or sent to telemetry.
- **`fespalier_sentry` is errors first, and the sink stays a sink.** The default sends events, breadcrumbs and the
  scope's names and no transaction; `tracing: true` is the opt-in, and each part of it goes behind it (a new span
  or measurement is never a default; streaming with `traceLifecycle: stream` is the same opt-in, never a second
  switch). No `autoFinishAfter`, no `waitForChildren` and no `startIdleSpan`: a screen's transaction or segment
  ends when its data arrives or when the next navigation starts, because Sentry starts a timer for each. The sink
  never imports OpenTelemetry: the link to a trace comes through `FespalierTelemetry.traceOf` and `linkTrace`
  (core), which `FespalierOtel` answers and `combine` carries; keep it that way. Nothing it sends may hold a
  segment value, a query value, a family key, an action's input or result, a data value, or a `FieldErrors`
  (`errors_test.dart` and `mapping_test.dart` check). Exception text is the app's, and breadcrumbs carry the
  class of an error, never its text. Since 0.19.0 the scope's names (transaction, `fespalier.route`, `otel.*`) and a streamed segment's name are set in `commit` and again, the same, at `end`. Breadcrumbs stay at `page` (and not found at `end`), so a commit makes none. Every finish, TTID, TTFD and `url.path` stay at `end`.
- **A hot reload swaps the route table (since 0.19.0, debug builds only).** The swap never goes through a closure made before the reload: the generated `_AppRoutesReload` overrides its methods, and an instance method runs the code that is current. A new `static final` or top-level `final` in `app.g.dart.jinja` is covered by `_kept` automatically (`cli/src/reload.rs` reads it, with no list to keep). A static that must follow the routes is not `final`: `_reload` assigns it again (`_matchers` does). The shells take their keys from `_keys` (a `ShellKeys` per `mount()`), so a reloaded layout keeps its pages. `_reload` also registers the deferred libraries again. Since 0.20.0 `AppRoutes.deferred` is a getter over `_deferred`, which `_allDeferred()` makes and `_reload` assigns again before it registers them, so a deferred route added or removed swaps; and a deferred page's import is `deferred as _page<Stem>` (`emit::deferred_prefix`), never `_i<n>`: the VM and DDC keep a deferred import's loaded state across a hot reload under its prefix's name, and a kept `_lib<Stem>` loads through the prefix it was made with (`fsp size` reads the same names). Since 0.20.0 every name a kept declaration has or spells follows its folder, never its position: `_data<Stem>`, `_lib<Stem>`, `_optimistic<Stem>`, `_page<Stem>` (a deferred page's import), `_action<Stem>_<function>` and the DevTools sites `d<Stem>` and `a<Stem>_<function>` take `Route::stem` (`resolve::assign_stems`: the folder in PascalCase, plus `_` and 8 hex digits of a hash of the folder when another folder with names has the same stem), and an import alias is `_e<alias_tag(library)>_<prefix>` (`extra.rs`; the library is the import's URI resolved by `extra::library_of`, never the file that spelled the type: the first file to constrain a segment can change, the library cannot). A new name in a top-level or static `final`, or in what one refers to, must do the same, or a route inserted before its folder refuses the swap again (`reload_tests.rs` adds routes everywhere and compares every other kept declaration); a positional name is fine only in a function, a const or the bodies `_routes()` and `_allMatchers()` build again (`_paramsN`, `_navN`, a guard's `g5@6`). Do not hide a name from `_kept`. A swap is told from a pop's or a `refresh()`'s restore in `leave.dart` by the route objects (`_isRouteSwap`): a restore is not enough. A rebuild that throws does not advance `RoutesReload`'s version, so the next reload tries it again. Everything is behind `kDebugMode`: a profile or release build has no listener, no `Expando` entry for the swap, and no swap. `fsp dev` predicts the same refusal with `Stamp::swaps_to` (`cli/src/reload.rs`): change both together.
