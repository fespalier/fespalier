# Where CrateStack's embedded mode fits

Since 0.10.0. CrateStack can also run **inside the app**: the same `.cstack` schema generates an embedded SQLite store
(`include_embedded_schema!` over `rusqlite`), reached from Flutter through FFI or `flutter_rust_bridge`
([cratestack.dev/guides/offline-first-sqlite](https://cratestack.dev/guides/offline-first-sqlite)). This page is what
that does and does not give a fespalier app. CrateStack is pre-1.0: re-read its guide for the version you run.

## It fits

- **As the durable store.** An app with a Rust crate on the embedded mode can implement `LocalStore` (a key and value
  table: `read`, `write`, `writeAll`, `delete`, `keys`, `clear`) over its own generated functions, so intents, owned rows
  and cursors live in SQLite. Or it can read **typed embedded tables directly** in `data.dart` (watch
  `crateStackRevision(tag)` so a sync rebuilds the read). The same schema drives the server and the device, so local rows
  have the server's shapes.
- **As a whole sync core.** An app whose Rust core already pushes, pulls and drains implements `SyncRunner` and keeps
  `autoSync`, the triggers, `Served` and `IntentOutcome` for the Dart side: override `syncRunner` with it. It skips
  `SyncEngine`.

## It does not fit

- **As a dependency of this package.** `flutter_rust_bridge` versions have to match across an app, and the bindings are
  generated by the app. The package stays pure Dart and imports no CrateStack code.
- **As a sync engine.** There is none: the embedded mode documents no built-in sync, and `@@audit` and `@@emit` do nothing
  there. The push, the pull and the merge are `RowSync` and `SyncEngine`, or your own `SyncRunner`.
- **As the source of truth for decisions.** Policies are parsed but **not enforced** in the embedded mode, so the client
  is untrusted: every decision stays an intent that the server makes.
- **On Flutter web.** The embedded wasm build needs OPFS in a dedicated worker, which Flutter's main isolate is not. On
  the web use `InMemoryLocalStore`, or `HiveLocalStore` on IndexedDB.
- **For a synchronous first frame.** FFI calls are asynchronous in Dart, so a read backed by the embedded store is one
  `loading.dart` frame. The in-memory and Hive stores keep their reads synchronous (`localOnly` and a `cacheFirst` hit
  are then on the first frame).

## What to implement

A `LocalStore` must **never evict**: an intent never expires and an unpushed row is the only copy of an edit, which is
why none of `fespalier_storage`'s budgeted storages is one. It answers with `FutureOr`, so an asynchronous store works
and costs the frame noted above. One writer per store: a second isolate (a background sync) needs a store that can be
opened safely from two.

## Where the code is

`packages/fespalier_cratestack/lib/src/local_store.dart` (the interface and `InMemoryLocalStore`), `hive_store.dart`
(`HiveLocalStore`, the reference), `sync_engine.dart` (`SyncRunner`). The guide is
[`docs/cratestack.md`](https://github.com/fespalier/fespalier/blob/main/docs/cratestack.md#8-where-cratestacks-embedded-mode-fits).
