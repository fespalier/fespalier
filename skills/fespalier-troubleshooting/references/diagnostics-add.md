# Diagnostics: `fsp add` and `fsp upgrade --app` (since 0.23.0)

As of 0.23.0 (`cli/src/add.rs` for the steps of `fsp add`, `cli/src/add/plan.rs` for its checks,
`cli/src/upgrade_app.rs` for `fsp upgrade --app`, `cli/src/pins.rs` for how both read the pins and
`cli/src/pubspec_edit.rs` for the pubspec edits). Messages are quoted as they are printed, to stderr, exit 1,
unless noted. The user documentation is [fsp add](https://github.com/fespalier/fespalier/blob/main/docs/cli.md#fsp-add) and
[Moving the app's pins](https://github.com/fespalier/fespalier/blob/main/docs/cli.md#moving-the-apps-pins); the commands
are in `fespalier`, `references/cli-and-config.md`.

Both commands check everything before they write anything: a refusal leaves the app as it was.

## `fsp upgrade --app`

`--check` exits 3 (not 1) when a ref would move. With `--json` the object is on stdout and every line below on stderr. The notes are printed as soon as `pubspec.yaml` is written, before `flutter pub get` runs, so the messages after them (a failing `pub get` or `gen`) come below the notes. When only `pubspec_overrides.yaml` has a ref to move (since 0.23.1), it takes the place of `pubspec.yaml` in the header, in the `Would write` line and in the `now pins` messages; when both have one (since 0.24.1), both are named there (`pubspec.yaml and pubspec_overrides.yaml: vA -> vB`, `pubspec.yaml and pubspec_overrides.yaml now pin vX.Y.Z`).

| `fespalier and its companions are pinned together, at one url and one release tag, and these are not:` then one line per package, then ``Pin them as fespalier is, then run `fsp upgrade --app` again``                                                                                                           | Each line is `{name} ({section}) comes from {how}, not from {url}` (a fork, or a folder) or ``{name} ({section}) is at `{ref}`, not a release tag like vX.Y.Z`` (a branch or a commit; an override at a commit or a branch is a note instead, since 0.23.1).
