# Diagnostics: `fespalier_auth` and its backends

Since 0.9.0 (`packages/fespalier_auth/lib/src/`; since 0.21.0 also `packages/fespalier_oidc`, `packages/fespalier_keypair`, `packages/fespalier_keypair_dpop` and `packages/fespalier_sign_keypair`: the OpenID Connect flow was part of `fespalier_auth` until 0.20.0, and DPoP lived in `fespalier_sign_keypair`). These are not `fsp` diagnostics: `fsp` has none for auth, because
the packages add no file kind, no `fespalier:` key and no command. They are the **run-time messages** of the
packages, quoted from the code (each is asserted by a test) and followed by the cause and the fix.
[`fespalier-guards`](../../fespalier-guards/SKILL.md) explains the rules behind them.

## OpenID Connect and Keycloak (`package:fespalier_oidc`)

`OidcException` (`OidcException: <message>`) is an answer `OidcBackend` cannot use. Each message below is asserted by a
test (`packages/fespalier_oidc/test/oidc_test.dart`); the descriptions Keycloak itself sends were read from a live
Keycloak 26.8.0 (`fespalier-guards`, its `auth-backends.md` page). None of them carries a token, a code or a `state`.

### With DPoP, and the request layer

| Message or symptom                                                                                                                   | Cause and fix                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OidcException: the server does not accept ES256 DPoP proofs (dpop_signing_alg_values_supported: RS256, PS256)`                      | The provider's discovery document does not list ES256 and the backend has a `proof`. The proofs `fespalier_keypair_dpop` makes are ES256                                                                                                                                                                                                                                  |
| `OidcException: the token endpoint answered HTTP 400: invalid_request: DPoP proof has already been used`                             | A proof was sent twice. A retrier **under** the session transport (a `RetryClient` or `dio_smart_retry` between the session and the network) re-sends the same headers: the same signature and the same `jti`. | `OidcException: the token endpoint answered HTTP 400: invalid_request: DPoP proof is not active`                                     | The device's clock is off from the server's (Keycloak 26.8.0 refused a proof 20 seconds ahead and 120 seconds either way, and took one 20 seconds behind). Fix the clock. A server or a proxy that sends a `Date` header lets `DpopProof` correct itself once (`clockCorrectionThreshold`, 5 seconds); Keycloak sends none                                                |
| `OidcException: ...: invalid_request: DPoP proof is missing`                                                                         | The client requires DPoP-bound tokens ("Require DPoP bound tokens" in Keycloak) and the backend has no `proof:`. Give `OidcBackend(proof: ...)` a `ProofOfPossession`                                                                                                                                                                                                     |
| `OidcException: ...: invalid_request: DPoP Proof public key thumbprint does not match dpop_jkt`                                      | The authorization request bound the code to one key and the code exchange was signed with another: the proof object was replaced, or its key regenerated, between the browser step and the exchange                                                                                                                                                                       |
| `AuthRejected: the server refused the session (invalid_grant: DPoP confirmation doesn't match DPoP proof)`                           | The refresh token is bound to a key this device no longer has (a restored backup, a wiped keychain). The user signs in again. `restoreAuth` already drops a session whose key is gone (`SignedOut(keyLost)`, from `OidcBackend.check`)                                                                                                                                    |
| An API answers 401 with `WWW-Authenticate: DPoP algs="...", error="invalid_token"` to every request, though the token is fresh       | The DPoP scheme was sent with no proof, or a proof with no `ath`, another `htu` or `htm`, another key, or a time that is off. | A guard against re-sent writes (an idempotency check, a `WriteGuardTransport`, Dio's `WriteGuard`) rejects a request after a renewal | `SessionTransport` sends a request again after a verdict that says so (a 401 and a renewal, a DPoP nonce). It was `isAuthReplay(request)` and `options.extra[authReplayKey]` until 0.20.0                                |
| A `DioException` whose `error` is an `AuthUnavailable`                                                                               | The renewal before or after a request could not run (offline, a 5xx). The session stays; `TransportAdapter` reports it as the request's error. Show "offline" and do not sign the user out                                                                                                                                                                                |
| A `DioException` whose `error` is an `AuthRejected` after a retry                                                                    | The session was refused or ended between two sends of one request: the renewal was refused, the user signed out, or another user signed in. The retry is not sent, on purpose (the request's `TransportMemo`; `SessionInterceptor` did it with `options.extra[authRefusedKey]` on 0.19.0 and 0.20.0). Send the user to sign in, then make the request again as a new call |

## `fespalier_sign_keypair` (device-signed sessions, since 0.21.0)

## Telemetry

`auth` spans (`#1 start auth restore backend=fake`, since 0.9.0) follow the installed sink: they need no
`telemetry: true`. The step of a renewal is `renew` and the scheme is `fespalier.auth.scheme` since 0.21.0 (`refresh` and a
boolean `fespalier.auth.dpop` until 0.20.0: a dashboard or alert that filters on either needs the new name). A sink that switches **exhaustively** over `TelemetryOp` stops compiling on 0.9.0 until it has an
`auth` case (`The type 'TelemetryOp' isn't exhaustively matched by the switch cases since it doesn't match the pattern 'TelemetryOp.auth'`):
add the case, or end the switch with `_ =>`. No span carries a token, an id, a claim, an e-mail or a URL
([`fespalier-observability`](../../fespalier-observability/SKILL.md), its conventions page).
