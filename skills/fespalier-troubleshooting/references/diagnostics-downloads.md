# Diagnostics: uploads that must not be sent twice (`fespalier_download_background`)

Since 0.16.0 (`packages/fespalier_download_background/lib/`). These are not `fsp` diagnostics: `fsp` has none for this
package, because it adds no file kind, no `fespalier:` key and no command. They are the **run-time lines** of the upload
engine, each read from the code and reproduced in a test (`test/uploads_test.dart`, "the two debug lines") before it was
quoted, followed by the cause and the fix. `<reason>` stands for the value in the line. The rules behind them are in
[`fespalier-downloads`](../../fespalier-downloads/SKILL.md), [`references/uploads.md`](../../fespalier-downloads/references/uploads.md).
Both lines are printed with `debugPrint` in debug builds only, never in release, and name no id, URL, path or header.

## Messages

| Message                                                                                                                                                                                                                                                                                      | Cause and fix                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fespalier_download_background: an upload was not started, because its entry could not be saved in the registry (<reason>): after a restart nothing would say it was sent` (debug)                                                                                                           | **U1.** `UploadStore.put` threw (a full disk, a folder `DownloadBases` cannot resolve; `<reason>` is `the registry file could not be written` for `FileUploadStore`, else the error's type). The upload ended `Failed(storage)` and **nothing was handed to the platform**: it is not an unknown outcome, and `retry(id)` tries again. Free the space, then `retry`. Before 0.16.0 the failed write was swallowed and the upload was sent with no record, so a restart could send it again                            |
| `fespalier_download_background: the uploads registry could not be loaded (<reason>), so an upload without an Idempotency-Key is not started: it may have been sent before and nothing remembers it. Restart the app, or call clearAccount after asking your server what it received` (debug) | **U2.** `UploadStore.load` threw at `open()`: the registry file exists and cannot be read (an I/O error, text that is not JSON, a version this one does not know; `<reason>` is `the registry file could not be read, or is not a registry this version knows`). `open()` still succeeds, but every upload **without** an `Idempotency-Key` ends `Failed(storage)` until the next `open()` reads the registry or `clearAccount()` deletes it (the files that were sent are not touched). An upload with a key is sent |
| `UploadStoreException: the registry file could not be written`, `UploadStoreException: the registry file could not be read, or is not a registry this version knows`                                                                                                                         | What `FileUploadStore` throws from `put` (the first) and from `load` or `put` (the second). The engine catches both and prints U1 or U2; you meet the text only when you call the store yourself. The file is left exactly as it is, so a person can look at it                                                                                                                                                                                                                                                       |

## Symptoms with no message

| Symptom                                                                                        | Cause and fix                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An upload is `Failed(other)` after a `500`, `502`, `503`, `504` or `408`, and `retry` is false | By design since 0.16.0 (on 0.15.0 it was `Failed(rejected)` and `retry` sent it again): a `5xx`, a `408` or a `499` says nothing about whether the server ran the write, so for an upload **without** an `Idempotency-Key` it is an unknown outcome (`outcomeUnknown(id)` is true). Ask your server whether it has the upload, then `remove(id)` and `start` it again, or add the header |
| An upload is `Failed(rejected)` and `retry` sends it again                                     | A `4xx` other than `408` and `499` (a `400`, `404`, `413`, `422`): the server refused it, so nothing was applied. Fix the request, then `retry`                                                                                                                                                                                                                                          |
| Every upload without a key is `Failed(storage)` after a restart, and nothing is sent           | U2: the registry file cannot be read. Restart the app (a transient read error clears), or `clearAccount()` after asking your server what it received. Do not delete the file blindly: it is the only record of which writes may have been sent                                                                                                                                           |
| `Failed(storage)` on every upload and the disk is not full                                     | U1 with another cause: `DownloadBases` throws for `DownloadBase.support`, or the folder is read-only. Run in debug and read the line for `<reason>`                                                                                                                                                                                                                                      |
