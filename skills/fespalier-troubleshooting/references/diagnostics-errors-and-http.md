# Diagnostics: `fespalier_dio`

Since 0.9.0 (`packages/fespalier_dio/lib/src/`). These are not `fsp` diagnostics: `fsp` has none for HTTP, because the
package adds no file kind, no `fespalier:` key and no command. They are the **run-time messages** of the package,
quoted from the code (each is asserted by a test in `packages/fespalier_dio/test/`), followed by the cause and the fix,
and then the symptoms that name no message. [`fespalier-data`](../../fespalier-data/references/http.md) explains the
rules behind them.

## Messages

| Message                                                                                                                                                                                                                                                              | Where                                                                                                            | Cause and fix                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fespalier_dio: PUT /me failed and was about to be sent again. A write is never retried, so its first error is returned. Give the retry interceptor WriteGuard.readsOnly(...) as its evaluator, or add an Idempotency-Key header to a write that is safe to repeat.` | M-D1: `WriteGuard`, `debugPrint` in debug builds, once per request                                               | A retry interceptor sent a write again and `WriteGuard` refused: the caller got the **first** error (a 503, a timeout) and nothing was sent twice. This is the guard working, and the line names the method and the **path** only (never the host, the query or a body). To stop the retrier from trying (and waiting out its delay), give it `WriteGuard.readsOnly(evaluator)`; for a write that is safe to repeat, send an `Idempotency-Key` header or `Options(extra: {WriteGuard.idempotent: true})` |
| `WriteNotRetried: PUT /me was sent again by an interceptor that runs before WriteGuard, so the error of its first send is unknown. A write is never retried. Call WriteGuard.install(dio) after adding every other interceptor: it puts WriteGuard first.`           | M-D2: `WriteNotRetried.toString()`, the `error` of the `DioException` the caller gets                            | An interceptor that re-sends a failed request (a retrier, a refresh) sits **before** `WriteGuard`, so it saw the error first and sent the write again before the guard had recorded the first one. Call `WriteGuard.install(dio)` **last**, after adding every other interceptor: it moves the guard to index 0, and the guard is never there twice                                                                                                                                                      |
| `fespalier_dio: the provider that started this request was disposed`                                                                                                                                                                                                 | M-D3: the reason of the `CancelToken` of `ref.cancelToken()`, the `error` of the `DioException` of type `cancel` | The page was left (or the provider rebuilt) while the request was in flight. This is `ref.cancelToken()` working, not a failure: see the symptom below                                                                                                                                                                                                                                                                                                                                                   |
| ``Request aborted by `abortTrigger` `` (`RequestAbortedException`)                                                                                                                                                                                                   | `package:http`'s own text, from `ref.abortTrigger()` and `ref.abortable(client)`                                 | The same as M-D3 for `package:http`: the provider that started the request was disposed or rebuilt. ## Symptoms

| Symptom                                                                                                                                                                       | Cause and fix                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DioException [request cancelled]: The request was manually cancelled by the user.` with `Error: fespalier_dio: the provider that started this request was disposed` in a log | `ref.cancelToken()` doing its job: a page was left, or a `data.dart` rebuilt, while its request was in flight, and the request fails **after** its provider is gone, so nothing reads it (with telemetry on, the data span ended as `disposed`, never as an error). Keep it out of an error reporter by ignoring `DioExceptionType.cancel`. If it surfaces on a page that is still on screen, something cancelled a token that page uses (a token shared with another provider, or `ref.cancelToken()` asked for a ref that was already replaced)                              |
| A request is **not** cancelled when its page is left                                                                                                                          | The token was asked for after an `await` (ask before the first one), or it was not given to the request (`cancelToken: cancel`), or it came from another provider's `ref`. For `package:http`: `ref.abortable(client)` was called after an `await`, or the client under it does not honour an abort trigger (`MockClient` leaves it to its handler). An `action.dart` is **not** cancelled when its page goes: its provider is kept alive until the write completes                                                                                                            |
| A write fails with its **first** error although a retry interceptor is installed                                                                                              | By design: `WriteGuard` refused the second send. The retrier is told nothing, so it tried; give it `WriteGuard.readsOnly(...)` as its evaluator, or mark a write that is safe to repeat with an `Idempotency-Key` header or `Options(extra: {WriteGuard.idempotent: true})`. A debug build prints M-D1 once per request                                                                                                                                                                                                                                                        |
| A write is **retried** although `WriteGuard` is installed                                                                                                                     | It is not first (`WriteGuard.install(dio)` was not the last call, or the interceptors were replaced afterwards), the request carries an `Idempotency-Key` header or `extra[WriteGuard.idempotent]`, or it is sent with a **new** `RequestOptions` each time (a retrier that builds a new request has no memory the guard can read): check `WriteGuard.isWrite(options)`                                                                                                                                                                                                        |
| `RetryClient` retries a `POST` on a 503                                                                                                                                       | The `RetryClient` has no `when: WriteGuardClient.readsOnly()`, or `WriteGuardClient` is **outside** it (it goes inside: `RetryClient(WriteGuardClient(inner), ...)`), or the client it wraps is not a `WriteGuardClient`. If you retry errors, wrap your rule in `whenError: WriteGuardClient.readErrorsOnly(...)` too: a write that threw is sent again otherwise                                                                                                                                                                                                             |
| A server's 422 (or 400) does not show under its form field                                                                                                                    | Check in order: `.withFieldErrors()` is on the action's own `Future` (an interceptor cannot do it); the status is in `statuses` (`{400, 422}` by default); the body is one of the shapes (`FieldErrorsDecoders.standard(decodedBody)` returns null for anything else: pass `decoder:`); the keys are the record's **field names** (`fieldName:`; `FieldNames.camelCase` turns `nick_name` into `nickName`, not `nickname`); only a **422** with a string `detail` or `message` becomes a message, never a 400. A key that is no field shows in `form.error`, not under a field |
| A field error shows under the wrong field, or two server keys land on one                                                                                                     | `fieldName` maps two keys to one name: the **first** wins. Map them apart                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Attempts multiply: a failing read is tried a dozen times                                                                                                                      | Two retry layers: Riverpod's data retry (`data_retry: inherit`, ten attempts) **times** an HTTP retrier. Keep one: the data retry with no HTTP retrier for reads, or an HTTP retrier for reads with `data_retry: none` in `pubspec.yaml`                                                                                                                                                                                                                                                                                                                                       |
| `Because every version of fespalier_dio from path depends on fespalier from git ... and fespalier_dio from path is forbidden.`                                                | `fespalier_dio` and `fespalier` have a different `url` or `ref` in the app's `pubspec.yaml`: give them the same one (the explanation is on the `fespalier_auth` page of this skill)                                                                                                                                                                                                                                                                                                                                                                                            |
| A test hangs on a Dio request, or `pump()` never starts it                                                                                                                    | Dio starts its chain with `Timer.run`: use a plain `test()`, `pumpAndSettle()`, or `pump(Duration.zero)` ([`fespalier-testing`](../../fespalier-testing/references/http.md))                                                                                                                                                                                                                                                                                                                                                                                                   |
