# Diagnostics: feature flags, storage and network

Since 0.9.0 (`packages/fespalier_flags/lib/`). These are not `fsp` diagnostics: `fsp` has none for these packages, because
they add no file kind, no `fespalier:` key and no command. They are the **run-time messages** of the packages, quoted from
the code (each is asserted by a test) and followed by the cause and the fix. `<key>`, `<fallback>` and `<error>` stand for
the value in the message. [`fespalier-guards`](../../fespalier-guards/SKILL.md) explains the rules behind the flag messages.

## `fespalier_flags`

The lines that start with `fespalier_flags:` are printed with `debugPrint` in debug builds only, and never in release.

| Message or symptom                                                                                       | Cause and fix                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `fespalier_flags: reading <key> threw, so its fallback (<fallback>) is used: <error>`                    | **F1.** A `FlagSource` read threw (an SDK that has not started, a platform error, a bug in a bridge). The flag is its `fallback` and nothing else breaks: a guard never throws because of a flag. Make the source answer from memory without throwing: start the SDK in `startup()`, or wrap a network-first vendor in `AsyncFlags`        |
| `fespalier_flags: the flag source's changes reported an error: <error>`                                  | **F2.** The `changes` getter threw, or its stream sent an error. The flags still read their current values; the subscription **stays** (an error does not cancel it), so later events still arrive. Fix the source's stream (a vendor stream that fails when the SDK is closed, a getter that starts something that can throw)             |
| `Bad state: FakeFlags has no value for "<key>"`                                                          | **F3.** `FakeFlags.strict` was asked for a key it does not hold: a typo in a key, or a flag the test did not set. Inside a `testWidgets` it also fails the test, through `FlutterError.reportError`, because the flag provider turns a throwing read into the fallback. Add the key to the fake, or fix the typo                           |
| `Bad state: FakeFlags has "<key>" = <value> (<runtimeType>), which is not a <bool\|String\|int\|double>` | **F4.** `FakeFlags.strict` holds a value of another type than the flag reads (`'labs': 'yes'` for a `BoolFlag`). A `double` flag accepts an `int`; an `int` flag does not accept a `double`. Give the fake the type the flag declares. A non-strict `FakeFlags` reads the fallback instead, silently                                       |
| `fespalier_flags: AsyncFlags' source failed, so the values meanwhile stay: <error>`                      | **F5.** The `Future<FlagSource>` an `AsyncFlags` waits for completed with an error (no network on a first launch, a vendor that refused its key). The flags keep answering from `meanwhile` (the fallbacks by default) and no switch event is sent. Retry from the app (a new `AsyncFlags`, or `updateOverrides`), or accept the fallbacks |

### Symptoms with no message

| Symptom                                                     | Cause and fix                                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A flagged entry still shows after the flag turned off       | The guard has `follow: false` (it reads once per navigation), the entry has `whenRefused: NavRefused.show`, the guard is the older `ProviderContainer c` form (read once, never follows), or the test has no `flagSource` override. Use a `Ref` guard that watches: `flagGuard(ref, flag, orElse: ...)` |
| Every flag is its fallback                                  | `startup()` does not return `flagSource.overrideWithValue(...)` (or a test has no override), or the key is misspelled: the source has no value for it. Use `FakeFlags.strict` in tests: a typo fails them                                                                                               |
| The page of a flagged route is blank on a cold deep link    | The guard answers a `Future`: a vendor's async API in it (PostHog's `isFeatureEnabled`). Copy the value into a `FlagSource` and read that; a guard that answers at once is in the first frame                                                                                                           |
| A cold deep link to a flagged route lands on `orElse`       | The vendor was not ready: the flag read its fallback. Await the vendor's local load in `startup()` (a `.timeout()` of your own if you wait for the network), or accept it                                                                                                                               |
| The flag's subscription outlives the page by one navigation | Expected: a guard that redirected stays subscribed until the next navigation (fespalier's rule for guards, pinned by `packages/fespalier_flags/test/guard_test.dart`). Nothing to fix                                                                                                                   |
