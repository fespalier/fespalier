# Diagnostics: feature flags, storage and network

Since 0.9.0 (`packages/fespalier_flags/lib/`). These are not `fsp` diagnostics: `fsp` has none for these packages, because
they add no file kind, no `fespalier:` key and no command. They are the **run-time messages** of the packages, quoted from
the code (each is asserted by a test) and followed by the cause and the fix. `<key>`, `<fallback>` and `<error>` stand for
the value in the message. [`fespalier-guards`](../../fespalier-guards/SKILL.md) explains the rules behind the flag messages.

## `fespalier_flags`

The lines that start with `fespalier_flags:` are printed with `debugPrint` in debug builds only, and never in release.

| Message or symptom                                                                                       | Cause and fix                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `fespalier_flags: reading <key> threw, so its fallback (<fallback>) is used: <error>`                    | **F1.** A `FlagSource` read threw (an SDK that has not started, a platform error, a bug in a bridge). The flag is its `fallback` and nothing else breaks: a guard never throws because of a flag. Make the source answer from memory without throwing: start the SDK in `startup()`, or wrap a network-first vendor in `AsyncFlags`        |
| `fespalier_flags: the flag source's changes reported an error: <error>`                                  | **F2.** The `changes` getter threw, or its stream sent an error. The flags still read their current values; the subscription **stays** (an error does not cancel it), so later events still arrive. Fix the source's stream (a vendor stream that fails when the SDK is closed, a getter that starts something that can throw)             |
| `Bad state: FakeFlags has no value for "<key>"`                                                          | **F3.** `FakeFlags.strict` was asked for a key it does not hold: a typo in a key, or a flag the test did not set. Inside a `testWidgets` it also fails the test, through `FlutterError.reportError`, because the flag provider turns a throwing read into the fallback. Add the key to the fake, or fix the typo                           |
| `Bad state: FakeFlags has "<key>" = <value> (<runtimeType>), which is not a <bool\|String\|int\|double>` | **F4.** `FakeFlags.strict` holds a value of another type than the flag reads (`'labs': 'yes'` for a `BoolFlag`). A `double` flag accepts an `int`; an `int` flag does not accept a `double`. Give the fake the type the flag declares. A non-strict `FakeFlags` reads the fallback instead, silently                                       |
| `fespalier_flags: AsyncFlags' source failed, so the values meanwhile stay: <error>`                      | **F5.** The `Future<FlagSource>` an `AsyncFlags` waits for completed with an error (no network on a first launch, a vendor that refused its key). The flags keep answering from `meanwhile` (the fallbacks by default) and no switch event is sent. Retry from the app (a new `AsyncFlags`, or `updateOverrides`), or accept the fallbacks |

### Symptoms with no message

| Symptom                                                     | Cause and fix                                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A flagged entry still shows after the flag turned off       | The guard has `follow: false` (it reads once per navigation), the entry has `whenRefused: NavRefused.show`, the guard is the older `ProviderContainer c` form (read once, never follows), or the test has no `flagSource` override. Use a `Ref` guard that watches: `flagGuard(ref, flag, orElse: ...)` |
| Every flag is its fallback                                  | `startup()` does not return `flagSource.overrideWithValue(...)` (or a test has no override), or the key is misspelled: the source has no value for it. Use `FakeFlags.strict` in tests: a typo fails them                                                                                               |
| The page of a flagged route is blank on a cold deep link    | The guard answers a `Future`: a vendor's async API in it (PostHog's `isFeatureEnabled`). Copy the value into a `FlagSource` and read that; a guard that answers at once is in the first frame                                                                                                           |
| A cold deep link to a flagged route lands on `orElse`       | The vendor was not ready: the flag read its fallback. Await the vendor's local load in `startup()` (a `.timeout()` of your own if you wait for the network), or accept it                                                                                                                               |
| The flag's subscription outlives the page by one navigation | Expected: a guard that redirected stays subscribed until the next navigation (fespalier's rule for guards, pinned by `packages/fespalier_flags/test/guard_test.dart`). Nothing to fix                                                                                                                   |

## `fespalier_storage`

Since 0.9.0 (`packages/fespalier_storage/lib/src/`). `<key>`, `<size>`, `<maxSize>`, `<n>`, `<name>` and `<error>` stand for
the value in the message. The `fespalier_storage:` lines are printed with `debugPrint` in debug builds only; S1 and S2 arrive
inside fespalier's own `fespalier: dataCache of <name> ...` line (its text is in
[`fespalier-data`](../../fespalier-data/references/freshness-and-cache.md)), and S6 and S7 are thrown.

| Message or symptom                                                                                                                                                                                                                                          | Cause and fix                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `fespalier_storage: the value saved under <key> is <size> characters, more than maxSize (<maxSize>), so it was not saved` (after `fespalier: dataCache of <name> could not save: `)                                                                         | **S1.** One value is over the storage's budget (`DataEntryTooLarge`). The route works and nothing is saved for it; its older copy is removed. Raise `maxSize` (the default is 1,000,000 characters for `PrefsDataStorage`, 4,000,000 for `HiveDataStorage`), save less (a smaller `toJson`), or use Hive for a large value. `<size>` counts the key and the header |
| `FormatException: fespalier_storage: a saved entry is not one this storage wrote (format fsc1)` (after `fespalier: dataCache of <name> could not read a saved value, dropped it: `)                                                                         | **S2.** An entry that is not `fsc1`: another version of the package wrote it, something else wrote under `fespalier.dataCache/`, or it was cut short. fespalier drops it, deletes it and loads: nothing to fix unless it repeats (then another writer shares the store)                                                                                            |
| `fespalier_storage: dropped <n> saved entries that could not be read` (debug)                                                                                                                                                                               | **S3.** At start the sweep found entries it cannot read and deleted them (see S2). Expected once after an upgrade that changes the format; if it appears at every start, something else writes under the prefix `fespalier.dataCache/`                                                                                                                             |
| `fespalier_storage: could not open shared preferences, so nothing is saved: <error>` (debug); in a test without `fakePrefsStore()` the error is `Bad state: The SharedPreferencesAsyncPlatform instance must be set.`                                       | **S4.** `PrefsDataStorage.open()` returned `null`: shared_preferences could not open, so the app starts and nothing is saved. In a widget test call `fakePrefsStore()` first (`setUp(fakePrefsStore)`, also before a test that boots `AppMain.run()` or `AppMain.root()`); in an app, read the error (a plugin that is not registered after a hot restart)         |
| `fespalier_storage: could not open the Hive box <name>, so nothing is saved: <error>` (debug); in a test the error is `MissingPluginException(No implementation found for method getApplicationCacheDirectory on channel plugins.flutter.io/path_provider)` | **S5.** `HiveDataStorage.open()` returned `null`. In a test use `HiveDataStorage(await memoryBox())`; in an app the cache directory could not be read or the box would not open (Hive truncates a corrupt file; a locked one is another process's)                                                                                                                 |
| `Invalid argument(s): PrefsDataStorage needs a SharedPreferencesWithCache without an allowList: the keys of a dataCache are not known in advance. Use PrefsDataStorage.open(), or create it with const SharedPreferencesWithCacheOptions().`                | **S6.** `PrefsDataStorage(prefs)` got a `SharedPreferencesWithCache` created with an `allowList`. Use `PrefsDataStorage.open()`, or create the instance with `const SharedPreferencesWithCacheOptions()` (no allowList). It is thrown by the constructor, before anything is swept                                                                                 |
| `Invalid argument (maxSize): must be more than 0: <value>` / `Invalid argument (maxEntries): must be more than 0: <value>`                                                                                                                                  | **S7.** A budget of 0 or less. `open()` throws it too (it is the app's mistake, not a store that cannot open). Give a positive `maxSize` (characters) and `maxEntries`                                                                                                                                                                                             |

### Symptoms with no message

| Symptom                                                        | Cause and fix                                                                                                                                                                                     |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A restart test shows `loading.dart`, not the saved value       | No `fakePrefsStore()` (S4: `open()` is `null`), the two `open()`s are in different tests, or the value passed `maxAge` (the fake clock) or its `DataCache.version` changed                        |
| The saved value is not on the first frame in the app           | `startup()` passes the `Future` (one `loading.dart` frame, then the saved value), or does not override `dataCacheStorage`, or the `data.dart` has no `dataCache`                                  |
| The previous user's data shows after signing in as another     | Nobody called `clear()` on sign-out: the next start shows what the storage saved. `await storage.clear()` when the session ends, and watch `authUserId` in a `data.dart` that belongs to the user |
| Old entries disappear on the web                               | `localStorage` is about 5 MB per origin, shared: past `maxSize` or `maxEntries` the entries written longest ago go first. Raise the budget, or use `HiveDataStorage` (IndexedDB)                  |
| `QuotaExceededError` printed after `could not save` on the web | localStorage is full (another script's data counts). The entry is dropped and the page works; lower `maxSize`, or use Hive                                                                        |
| A second isolate's writes are not seen until the next start    | One writer per store: the index is built at start and never saved. Write from one isolate, or accept it                                                                                           |

## `fespalier_connectivity`

Since 0.9.0 (`packages/fespalier_connectivity/lib/src/`). `<error>` stands for the error in the message. The
`fespalier_connectivity:` lines are printed with `debugPrint` in debug builds only. C3 is Flutter's own report, which a
widget test turns into a failure.

| Message or symptom                                                                                                                                                                                                                                                                                                                        | Cause and fix                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fespalier_connectivity: the connectivity stream reported an error: <error>` (debug)                                                                                                                                                                                                                                                      | **C1.** `ConnectivitySource.changes` sent an error, or the getter threw. The state is kept and the subscription stays, so later changes still arrive. For the plugin it is a platform error; for your own source, fix its stream                                                                                                                                                                                                                                           |
| `fespalier_connectivity: checking connectivity failed: <error>` (debug); with no plugin the error is `MissingPluginException(No implementation found for method check on channel dev.fluttercommunity.plus/connectivity)`                                                                                                                 | **C2.** `ConnectivitySource.check()` failed or threw: at the start (the web's and any platform's first state), or on a resume (the iOS repair). The state is kept, and `hasNetwork` stays `true` until a state is known. In a widget test it comes with C3: override `connectivitySource` with a `FakeConnectivity`                                                                                                                                                        |
| Flutter's report `══╡ EXCEPTION CAUGHT BY SERVICES LIBRARY ╞══` `The following MissingPluginException was thrown while activating platform stream on channel dev.fluttercommunity.plus/connectivity_status:` `MissingPluginException(No implementation found for method listen on channel dev.fluttercommunity.plus/connectivity_status)` | **C3.** A widget test reached the plugin, which a VM test does not have: something watched `hasNetwork` or `networkConnectivity`, or built a `refetchOnReconnect` provider with `ConnectivitySignal` as `reconnectSignal`, with `connectivitySource` not overridden. `connectivitySource.overrideWithValue(FakeConnectivity())` in `pumpRouter`'s overrides (and in `fsp test`'s `setup.dart` when a route's page shows a banner). Without it the test fails on the report |

### Symptoms with no message

| Symptom                                                                        | Cause and fix                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `refetchOnReconnect` never reloads                                             | `startup()` does not override `reconnectSignal` (`reconnectSignal.overrideWith(ConnectivitySignal.new)`; in a test, `pumpRouter` does not run `startup()`), or the value is younger than its `staleTime`, or the network went from Wi-Fi to mobile (not a reconnect: the device never had none), or the first answer was the offline one (not a reconnect either) |
| An offline banner stays up after the network came back                         | A hand-written signal that listens to the stream only: iOS drops connectivity events while the app is in the background, and the web sends none on listen. `fespalier_connectivity` asks `check()` again on each resume; use it                                                                                                                                   |
| The banner says "No network" but the API answers (or the other way round)      | Connectivity is not reachability: a VPN reported as `other`, the iOS simulator's missed Wi-Fi events, a captive portal. `hasNetwork == false` is "no interface is up"; `true` promises nothing. For "does my server answer", use the reachability recipe in `fespalier-data`                                                                                      |
| A reload on a captive portal that fails                                        | Expected: `refetchOnReconnect` fires on connectivity, the reload fails, and `keepDataOnError` keeps the page. Show the load's own error                                                                                                                                                                                                                           |
| A reconnect loads the same data twice                                          | It does not: a reload already under way is not stale. Two providers of the same data, or an `invalidate` of your own beside it, would                                                                                                                                                                                                                             |
| A test hangs or says `A Timer is still pending` with a raw `ProviderContainer` | A container of your own disposes on a zero-duration timer: `await tester.pump(const Duration(milliseconds: 1))` before the test ends, and the same where a plain `pump()` shows no reload                                                                                                                                                                         |
