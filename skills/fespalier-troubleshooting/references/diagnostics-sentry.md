# Diagnostics: `fespalier_sentry`

Since 0.9.0 (`packages/fespalier_sentry/lib/src/`). These are not `fsp` diagnostics: `fsp` has none for Sentry, because the package
adds no file kind, no `fespalier:` key and no command. They are the **run-time messages** of the package, quoted from the code
(each is asserted by a test), followed by what to look at when Sentry shows less, or more, than expected.
[`fespalier-observability`](../../fespalier-observability/references/sentry.md) explains the rules behind them.

## Messages

| Id   | Message                                                                                                                                                                                                              | Cause and fix                                                                                                                                                                                                                                                                                                                                                    |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M-S1 | `Invalid argument (tracesSampleRate): must be between 0 and 1: 1.5`                                                                                                                                                  | An `ArgumentError` from `FespalierSentry.configure`: `tracesSampleRate:` is outside 0 to 1 (or not a number); nothing was set on the options. Pass a rate such as `0.1`, or leave it out: it is null (no tracing) unless `tracing: true`, which samples 1.0 in debug and 0.1 in release                                                                          |
| M-S2 | `fespalier_sentry: Sentry's traceLifecycle is stream, which this version makes no spans for. Errors and breadcrumbs are still sent; use SentryTraceLifecycle.static for screen transactions.`                        | `debugPrint`, in debug builds only, once per sink, when `FespalierSentry(tracing: true)` meets `options.traceLifecycle = SentryTraceLifecycle.stream`. Sentry's `startTransaction` does nothing in that mode, so the sink makes no spans; events and breadcrumbs are unaffected. Leave `traceLifecycle` at `static` for `tracing: true`, or drop `tracing: true` |
| M-S3 | `fespalier_sentry: tracing: true needs Sentry to sample transactions, and tracesSampleRate is not set, so no transaction is sent. Pass tracing: true to FespalierSentry.configure, or set options.tracesSampleRate.` | `debugPrint`, in debug builds only, once per sink, when `FespalierSentry(tracing: true)` runs on an SDK with neither `tracesSampleRate` nor `tracesSampler`. The sink makes no spans (events, breadcrumbs and the scope's names still work). Pass `tracing: true` to `FespalierSentry.configure` as well, or set `options.tracesSampleRate`                      |

## Symptoms

| Symptom                                                                                                             | Cause and fix                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Nothing at all in Sentry                                                                                            | An empty `SENTRY_DSN` (`const String.fromEnvironment` without `--dart-define`: the SDK is off and the sink returns at once), no `FespalierTelemetry.install(FespalierSentry())` before the router is built, no `fespalier: telemetry: true` plus `fsp gen`, or the install ran before `SentryFlutter.init` finished. Install in `startup()` |
| Events, but no `fespalier.route`, `.file` or `.operation` tags                                                      | Another integration reported the error first and Sentry's deduplication dropped the tagged one: `sentry_dio`'s `FailedRequestInterceptor` captures a failed request before `data()` throws. Use `dio.addSentry(captureFailedRequests: false)`; the scope's `fespalier.route` tag and the transaction name still mark theirs                 |
| Events have no `otel.trace_id`                                                                                      | `fespalier_otel` is not in the same `FespalierTelemetry.combine` (a second `install` replaces the first), or the OpenTelemetry SDK was not up when the operation started (`FespalierOtel(isReady:)` false: no span, so no trace), or the app does not run `fespalier_otel` at all                                                           |
| **Two `ui.load` transactions per screen** (`tracing: true`)                                                         | A plain `SentryNavigatorObserver()` is in `routerObservers` and makes one per push. Use `FespalierSentry.navigatorObserver()` (`enableAutoTransactions: false`), or `FespalierSentry(tracing: true, transactions: false)` to let the observer make them                                                                                     |
| A transaction named `navigate`                                                                                      | Something else bound a transaction to the scope (`bindToScope: true`) while the navigation was open, so the sink could not rename its own: the scope's span was no longer it. Do not bind one during a navigation; the screen's name is still on the scope and on every event                                                               |
| The first screen has no fespalier spans on Android or iOS (`tracing: true`)                                         | By design: Sentry's own app start is that screen's `ui.load`, and a second one would duplicate it. The sink still names the scope and reports its time to full display to it. `enableStandaloneAppStartTracing: true` (Sentry 9.26.0, experimental) makes the first screen an ordinary one                                                  |
| `tracing: true`, but no transaction arrives                                                                         | M-S3 (the SDK samples nothing), M-S2 (`traceLifecycle: stream`), the release sample rate of 0.1, or a screen whose data never arrived: it ends when the next navigation starts, and a navigation that a newer one superseded is dropped                                                                                                     |
| HTTP spans are under the screen's transaction, not under the `data` span                                            | In static lifecycle Sentry's HTTP integrations parent to the scope's span, which is the navigation. Under `fespalier_otel` they are under the data span                                                                                                                                                                                     |
| No release health on the web                                                                                        | The SDK starts web sessions only with a `SentryNavigatorObserver`: add `FespalierSentry.navigatorObserver()` to `routerObservers`                                                                                                                                                                                                           |
| Uncaught async errors never reach Sentry, with `otel_zone`                                                          | `OtelZone.runGuarded` is the outer zone: its handler sends the error to Talker only. Run `SentryFlutter.init(appRunner: body)` as `zone()` and start the SDK with `observability.start()` in `startup()`; Sentry must be the outermost zone                                                                                                 |
| The query or the fragment of a URL is in Sentry                                                                     | `FespalierSentry.configure` was not called, or `recordQueries: true`, or a `beforeBreadcrumb`, `beforeSend` or `beforeSendTransaction` the app set **after** it replaced its callbacks (set the app's own first: `configure` keeps and runs them). Exception text is not scrubbed: redact in `beforeSend`                                   |
| Two breadcrumbs for one page change                                                                                 | `observerBreadcrumbs: true`, or `SentryNavigatorObserver`'s breadcrumbs added after the options were configured. `configure` drops the observer's, since the sink's say the same with the pattern                                                                                                                                           |
| A `jni` version conflict at `flutter pub get`                                                                       | `sentry_flutter` pins `jni` exactly (`0.14.2` in 9.30), which conflicts with another plugin that wants a different one (`cronet_http`, `native_dio_adapter`). Not fespalier's dependency to change: align the other plugin, or use the `sentry_flutter` release that matches                                                                |
| `fespalier_sentry` does not resolve: `Because every version of fespalier_sentry from path depends on fespalier ...` | The same mismatch as `fespalier_otel`: `fespalier` and `fespalier_sentry` must be the same repository dependency (same `url`, same `ref`): `references/diagnostics-observability.md`                                                                                                                                                        |
